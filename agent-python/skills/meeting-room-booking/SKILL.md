# 会议领域 Skill

## 意图边界

- “有没有空会议室”“查会议室”“看看已有预约”属于查询类动作。
- “订会议室”“安排会议”“预约一间会议室”属于创建类动作。
- “改时间”“换会议室”“修改刚才的预约”属于修改类动作，必须有唯一的已有预约事实。
- “取消会议”“撤销预约”属于取消类动作，必须有唯一的已有预约事实。

具体 action_id 必须从当前 route_conversation 工具 schema 的 enum 选择；本 Skill 不定义动作名称。

边界样例：

- “取消刚才那个会议”仍是取消语义，即使当前没有预约编号；此时应澄清来源预约，不能改成查询。
- “把会议室换成能坐 20 人的房间”是修改语义，缺少来源预约时应澄清。
- “查一下最近的会议预约记录”是查询语义，但仍需要明确查询时间范围。

字段提取样例：

- “明天 10 点到 11 点订一间会议室，主题是周会”应提取创建所需的 `subject`、`start_time` 和 `end_time`。
- “取消预约编号 123 的会议”应提取 `source_booking_id=123`，但该编号仍需来自当前用户授权查询事实。

## 澄清策略

- 创建预约至少需要主题、开始时间和结束时间；缺少必填信息时先澄清。
- 相对日期先依据当前业务时间转换，不因为用户没有写公历日期就重复追问。
- 多个会议或多个候选预约无法唯一确定时，要求用户选择，不猜业务 ID。
- 会议室冲突和参会人日程冲突都必须保留；更换会议室不能解决参会人冲突。
- 草稿、待确认和已提交是不同状态，不能混写成“预约成功”。

Skill 只提供语义、字段提取和澄清方式；Action、权限、审批、幂等和执行边界由代码契约决定。
